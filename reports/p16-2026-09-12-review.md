## Confirmed findings and resolution

### Descendant traversal finding (resolved)

- **P2 — Descendant revocation silently stops after 100 generations.** In `apps/web/src/server/auth/tokens.ts`, `revokeDescendants` uses `depth < 100` and returns without checking whether a frontier remains. After 101 legitimate rotations of token A, replaying A (or logging out using A through the newly strengthened descendant-revoking logout path) revokes only through depth 100; the latest token at depth 101 remains usable. The new users-row lock prevents races but does not close this traversal gap. Use a visited-ID guard and traverse until exhaustion, or a complete recursive query, and add a chain-longer-than-100 regression for replay/logout. Independent auth edge scout reported this; lead notified immediately. Bulk password-reset revocation is not affected by this particular bound.

Resolved in the final source: `tokens.ts:176–195` traverses until the finite frontier is exhausted and tracks visited IDs to prevent cycles; it no longer imposes a generation cap. Inspected `security/rule-07-refresh-rotation.test.ts:121–131`, which performs 101 actual rotations, replays the root, and requires the latest token to be revoked. The lead's updated log records 12/12 tests passing at 00:09:27. No new defect found in the fix.

### Important (resolved after re-review)

- **P2 — SMTP work runs before request throttling.** `apps/web/src/app/api/auth/[...all]/route.ts:42–50` invokes `verifyPasswordResetSmtp()` before calling the Better Auth handler. That helper (`server/auth/password-reset-mail.ts:92–99`) opens a fresh SMTP connection and authenticates. Better Auth's `onRequestRateLimit` only runs inside the downstream handler. Consequently malformed requests, requests with an invalid Origin, and requests above the three-per-minute limit all create SMTP connections; an SMTP outage returns 503 without ever entering the rate limiter. An unauthenticated caller can consume provider connection/auth quotas and keep sockets open for the configured 10–15 second timeouts. Move the availability check after framework request limits and before account lookup, or enforce an independent bound before this external I/O. Add a negative-control assertion that throttled requests create no SMTP connection.
- **P2 — Resetting a password in a signed-in browser leaves a redirect loop.** `apps/web/src/server/auth/config.ts:91` enables database-session revocation, but the reset response returned through `app/api/auth/[...all]/route.ts:52` does not expire browser cookies. The installed Better Auth reset handler deletes database sessions and returns JSON without calling `deleteSessionCookie`. A browser holding its old `better-auth.session_token` can reach `/forgot-password` or `/reset-password`, successfully reset, and click the rendered login link. `src/proxy.ts` redirects `/login` to `/me` based on cookie presence; `/me` rejects the now-revoked session and redirects back to `/login`. Expire the current browser's session and refresh cookies on successful reset using the secure-prefix/path handling already present in `/api/auth/logout`. Add a browser or response-cookie regression test starting with a valid signed-in session.

Both findings were fixed by the backend implementer and reread independently. The SMTP check now runs in the configured Better Auth `before` hook, after HTTP router throttling, with explicit payload validation. The `after` hook only clears cookies after a `{ status: true }` reset result and uses the framework's `deleteSessionCookie`, which preserves the configured secure cookie name and attributes. Refresh cookie expiry keeps `/api/auth` as its path. Installed framework code (`api/index.mjs`, `api/dispatch.mjs`, `cookies/index.mjs`) confirms hook ordering, result representation, and cookie behavior. Backend reports typecheck plus 21/21 scoped tests passing, including fourth-request 429 with unchanged SMTP connection count and real reset-response cookie expiry. Those test executions belong to the backend agent; this review verified the source paths.

## Credential lifecycle follow-up

The previous bulk refresh revocation could miss a child inserted by an in-flight `rotateRefreshToken` call: the old claim and successor insert were separate awaited statements. The lead replaced that flow with a users-row `FOR UPDATE` lock shared by rotation, refresh bootstrap, credential revocation, and logout. Rotation now claims and inserts in one transaction; bootstrap rechecks the referenced session's user and expiry after obtaining the lock; reset removes sessions and verification codes while holding the same lock. All inspected paths use users-before-refresh lock ordering. This closes the traced platform refresh race without a migration. The review does not equate this lock with an atomic transaction around every framework sign-in/password-reset operation.

Inspected `refresh-races.integration.test.ts` and `reports/p16-2026-09-12-refresh-tests.log`: the lead's two suites pass 11/11. Tests use real PostgreSQL and pause before successor INSERT or session DELETE. Both now explicitly assert that the competing operation remains pending while the old state is visible, then assert that the successor is revoked or bootstrap returns null. The bootstrap pending assertion was strengthened after review and rerun successfully at 23:59:07.
